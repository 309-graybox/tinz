# 1. Predictable Camera-Relative Movement

Forward input follows the camera view projected onto the movement plane.

- Movement is always recalculated relative to the current camera, including automatic camera rotation.
- Holding input does not lock a world-space heading.
- Manual camera rotation should change movement direction smoothly, without abrupt trajectory jumps.
- Automatic rotation can curve the trajectory during sustained sideways input. Backward input is mirrored along the camera-forward axis so that backward diagonals preserve the same left/right turn direction as forward diagonals.

The always-camera-relative rule was confirmed on 2026-10-23. See [[Автоповорот Камеры]] for acceptance scenarios.

# 2. Context-Dependent Behavior

The camera adapts to geometry and player actions.

- Dedicated zones may change position, viewing angle, and rotation freedom.
- During eligible movement, automatic Yaw assistance follows forward and sideways movement. Movement in the rear camera hemisphere uses its mirrored longitudinal direction while preserving the lateral sign.
- Lock-on, cinematic orientation, and movement-based assistance require explicit ownership rules rather than silently competing.

The camera should display information relevant to the current action. Detailed arbitration remains a design decision.

# 3. Collision Handling

Camera collision must not cause visual shock or loss of control.

- Near solid walls, the camera moves toward the character predictably and returns smoothly when clear.
- Other obscuring geometry may use the separately specified masking mechanics.
- Collision must not introduce abrupt position or viewing-angle changes.

See [[Camera Collision]], [[Smooth Zoom After Collision]], and [[World Space Masking]].

# 4. Manual Camera Priority

Manual camera rotation has priority over assistance.

- Manual response should be responsive and configurable.
- Intentional manual rotation immediately suppresses automatic angle correction.
- Resumption requires the documented delay.
- Character movement input is distinct from camera input.
- Input filtering and optional rotation lag must not reverse this priority.

Yaw assistance and Pitch recovery have separate timing contracts. See [[Автоповорот Камеры]] and [[Восстановление Камеры]].

# 5. Guiding Attention

The camera helps reveal important gameplay elements.

- A designated zone may gently redirect the view toward an objective or route according to its control policy.
- Movement and jump framing can emphasize inertia and landing.
- Preset configurations can provide different framing.

Each behavior must specify how it acquires and releases camera control.

# 6. Smooth Motion

Camera motion should remain visually comfortable.

- Following may use a spring or an authored response curve to create controlled lag.
- Automatic turns need explicit activation rules and a defined response model.
- Smoothing stages must have distinct purposes.
- Equivalent input should produce equivalent behavior across frame rates.
- The existing design calls for slight FOV narrowing during strongly accelerated movement; its tuning is separate from Yaw assistance.

The current auto-rotation response uses exponential Yaw correction, a maximum angular speed, and a separate 95-percent ramp time. Manual input is the only event that starts the resume-delay timer.
